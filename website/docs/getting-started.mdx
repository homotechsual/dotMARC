# Getting Started

dotMARC needs **two separate** Microsoft Entra app registrations, one to read the DMARC reports
mailbox and one to sign people in to the dashboard. Do not reuse one for both purposes. Each
deployment guide below walks you through creating them at the point you need them, so pick how you
want to run dotMARC first.

## Configure

:::warning[This is a reference, not a setup guide]

This table only explains what each setting means. It is not the place to set dotMARC up, and following it
on its own will leave you with a half-configured install. All setup instructions, including creating the
Entra app registrations and supplying these values, are in the deployment guides:
[Deploy with Docker](./deploy-with-docker.mdx) or [Deploy to Azure](./deploy-to-azure.mdx).

:::

Everything dotMARC reads is set through configuration. Both deployment guides set these for you.

## Choose how to run it

Both paths run the exact same product image and cover the same ground end to end - pick whichever
fits how you already operate:

| | [Deploy with Docker](./deploy-with-docker.mdx) | [Deploy to Azure](./deploy-to-azure.mdx) |
| --- | --- | --- |
| Best for | Self-hosters: your own hardware, a home/office server, or any VPS | Teams already running infrastructure on Azure |
| You manage | The host, Docker, TLS (a bundled Caddy setup handles this for you) | Nothing beyond the app config - Container Apps handles the rest |
| Database | PostgreSQL container, your own volume/backups | Managed Azure Database for PostgreSQL Flexible Server |
| Cost model | Whatever your own hardware/VPS costs | Pay-as-you-go Azure resources |

Not sure? [**Deploy with Docker**](./deploy-with-docker.mdx) is the faster path to a first working instance - a single
`docker compose` command gets you a complete stack, including HTTPS. [**Deploy to Azure**](./deploy-to-azure.mdx) trades a
bit more setup for infrastructure you don't have to maintain yourself.

### Which services are sending

Above the per-IP table, the Sources tab has a **Senders** table with one row per sending service your
reports point to, such as Microsoft 365, Google Workspace or Mailchimp:

* **Messages and Share** are how much of the domain's mail the service sent in the last 30 days.
* **Evidence** is a score of the signals dotMARC found for that service, with a label of strong,
  moderate or weak. It is not a probability, and it never reaches 100%. Open a row to see the signals
  behind it.
* **Pass rate and Failing** show how much of its mail passed DMARC, and how much was quarantined or
  rejected.
* **Fix** says what is failing and what to do about it, naming the service. It appears only when some
  of that service's mail is failing.

The signals are:

* an SPF or DKIM domain in the report that belongs to the service
* the DKIM selector the service is known to use
* who owns the sending IP
* the service being included in the domain's own SPF record, which is the weakest signal because it
  shows what is allowed to send, not what did

Mail from a properly set up Microsoft 365 or Google Workspace signs as your own domain, so it is
recognised by its IP owner and DKIM selector instead.

Sources that match no known service are listed last as **Not matched to a known service**. That means
dotMARC could not match them, not that they are bad. The matching is worked out each time you open
the page, so it improves as dotMARC learns more services, and it also names the service in failure
recommendations, client reports, the client portal and the `service` field of the sources API.

### Decide which senders are authorised

The **Decision** column is where your team records what it has decided about a sender on this domain:

* **Authorised**: it should send as this domain.
* **Unauthorised**: it should not.
* **Under review**: you are still finding out, for example waiting for the client to answer.
* **Unreviewed**: nobody has decided yet. This is the default.

Select a status to change it, add an optional note, and save. A decision is a label for your team. It
never changes DNS and never blocks mail, because your DMARC policy decides what receivers do. The row
shows who decided and when, and every change is recorded in the [audit log](./audit-log.mdx).

The **Fix** column changes with the decision:

* An **Unauthorised** sender is not asked to be fixed. If its failing mail is all blocked, the row says
  your policy is blocking it. If some was still delivered, it says how much and what your policy
  means for that: at `none` nothing is blocked, at `quarantine` it goes to spam, and at `reject`
  receivers should refuse it.
* An **Unauthorised** sender whose mail passes DMARC is flagged first, because it means the sender
  authenticates as your domain. Decide whether it should be authorised, or remove its access.
* An **Authorised** sender gets no fix while its mail passes. If some of it fails, the row says you
  authorised it but it is failing, and keeps the fix.

Open a service row to decide on a single IP address. An IP decision overrides the decision on its
service, and the other IPs show "same as the service". A source in the Not matched row has no
service, so you decide on its IPs.

Changing decisions needs the **SenderReview** permission, which the Admin role has. Custom roles can be
given it on the Access page. Anyone who can see the domain can see the decisions.

The domain's Overview tab shows how many senders still have no decision, with a **Review** button that opens the
Sources tab, and it goes away once every sender has one. The sources API returns each source's decision in a read-only
`decision` field: `Authorised`, `UnderReview`, `Unauthorised` or `Unreviewed`. [Client reports](./client-reports.mdx)
say how much mail from unauthorised senders was blocked or delivered.

dotMARC also raises two [sender alerts](./alerts.mdx#sender-alerts): one when a new sender appears
that nobody has reviewed, and one when mail from a sender you marked Unauthorised is being delivered.

#### Set an answer once for many domains

You don't have to decide the same sender on every domain. Decisions can be made at three levels, and the
most specific one wins:

1. **The domain's own decision**, on the service or on a single IP. It overrides everything below.
2. **The group's defaults**, set from **Manage > Groups** with the **Sender defaults** button on a group.
3. **The baseline**, set from **Manage > Sender baseline**. It applies to every domain.

For example, authorise Microsoft 365 in the baseline, mark it Unauthorised in the defaults of a client
group that has moved away from it, and authorise it again on one domain of that client that still uses
it. Each row in the Senders table says where its decision came from: set on this domain, from a group,
or from the baseline. Choosing **Reset to inherited** in the dialog removes the domain's own decision, so
the row falls back to the level below.

* A baseline or group decision only matters on a domain whose reports show that service. Nothing is
  added to domains that don't use it.
* If a domain is in several groups that disagree, the most cautious decision wins: Unauthorised, then
  Under review, then Authorised. The row says which groups disagree, and a decision on the domain itself
  settles it.
* The baseline can be changed only by someone who isn't limited to particular groups. A person limited to
  some groups can change the defaults of their own groups, and no others.
* If a service later leaves dotMARC's list of known services, its decision is kept and shown as "no longer
  recognised", with a button to remove it.

# Getting Started

dotMARC needs **two separate** Microsoft Entra app registrations, one to read the DMARC reports mailbox and one to sign people in to the dashboard. Do not reuse one for both purposes. Each deployment guide below walks you through creating them at the point you need them, so pick how you want to run dotMARC first.

## Configure

:::warning[This is a reference, not a setup guide]

This table only explains what each setting means. It is not the place to set dotMARC up, and following it on its own will leave you with a half-configured install. All setup instructions, including creating the Entra app registrations and supplying these values, are in the deployment guides: [Deploy with Docker](./deploy-with-docker.mdx) or [Deploy to Azure](./deploy-to-azure.mdx).

:::

Everything dotMARC reads is set through configuration. Both deployment guides set these for you.

## Choose how to run it

Both paths run the exact same product image and cover the same ground end to end - pick whichever fits how you already operate:

| | [Deploy with Docker](./deploy-with-docker.mdx) | [Deploy to Azure](./deploy-to-azure.mdx) |
| --- | --- | --- |
| Best for | Self-hosters: your own hardware, a home/office server, or any VPS | Teams already running infrastructure on Azure |
| You manage | The host, Docker, TLS (a bundled Caddy setup handles this for you) | Nothing beyond the app config - Container Apps handles the rest |
| Database | PostgreSQL container, your own volume/backups | Managed Azure Database for PostgreSQL Flexible Server |
| Cost model | Whatever your own hardware/VPS costs | Pay-as-you-go Azure resources |

Not sure? [**Deploy with Docker**](./deploy-with-docker.mdx) is the faster path to a first working instance - a single `docker compose` command gets you a complete stack, including HTTPS. [**Deploy to Azure**](./deploy-to-azure.mdx) trades a bit more setup for infrastructure you don't have to maintain yourself.

### Inventory and filters

Inventory supports **All domains** and **By group**. Both use exactly one **Filters** panel above the list. It contains Group, Tag, domain search, report status, pass rate, last report, monitored state, DMARC target and DNS status filters. Inventory also includes minimum report count and PSA company override filters. Filters apply to every group together; groups without matches disappear. A domain in several groups may appear in each, but the matching-domain count counts it once.

Collapsing Filters leaves the criteria active and shows a summary beside the button. **Clear all filters** clears the current criteria without changing your access scope or saved default. **Save as my default** remembers structured criteria, view and sort for that page; text searches are not saved as defaults. Dashboard and Inventory defaults are independent. Existing saved Dashboard list preferences migrate to Inventory.

Use **Show management columns** for group/tag assignment, PSA overrides, report counts and deletion, subject to your existing permissions. Manual drag ordering requires All domains with no active filters or column sort. Add and Import are available with domain-creation permission. **Manage > Tags** now owns tag creation, renaming, colours and deletion, separately from Groups.

Opening a domain and using its **Back** button or browser Back restores the list's filters, sort and position for up to 30 minutes in the same tab. Fresh navigation starts from that page's saved default. A directly opened domain falls back to Inventory.

### Dashboard action centre

The summary cards and both domain queues share the single **Filters** panel and your authorised group scope. Large numbers, labels and reporting windows are shown consistently; a missing pass rate reads **No data**, not 0% or an all-clear.

**Domains needing attention** explains each confirmed DNS/configuration problem, overdue expected report or unresolved sender decision, with links to the relevant domain tab. Confirmed problems appear first, then sender decisions, then unchecked evidence, with deterministic name tie-breaking. Click an action, sender-review or needs-checking card to narrow this queue; **Show all attention** restores the whole queue without changing the domain filters. This queue category survives Back navigation but is not saved as a domain-filter default or carried into Inventory. Unknown checks are labelled **Needs checking**, not confirmed failures. DKIM selectors and MTA-STS are assessed only when configured, and null-SPF domains do not require incoming DMARC reports, usable DKIM selectors or MTA-STS. This is a view of existing observations, not the deferred baseline-aware security score.

Sender-review counts use the same unresolved-decision resolver as Domain Overview, including domain/group/default decisions: **Under review** is already a decision, not an unresolved sender. Counts cover 30 days and are per sender per domain, not globally unique organisations. Dashboard uses cached sender attribution without performing new DNS or IP lookups; Domain Sources can refine attribution when its live lookups finish.

The attention queue also has multi-select **Issue categories**: **DNS/configuration**, **Missing reports**, **Sender review** and **Needs checking**. Select any combination to match a domain in any selected category, counted once. **All** clears the category selection. Counts show matching domains under the current shared domain filters; they can overlap and should not be added together. Category choices survive Back but do not affect summary cards, investigations, saved domain defaults or Inventory.

Each attention row separates the domain name, labelled issue descriptions, action links, sender-review work and quieter report metadata. **Add domain** scrolls to and focuses Inventory's creation field after it is ready, preserving the current domain/group filters. The form validates names and duplicates before saving.

**Quarantines and rejects to investigate** is separate from configuration problems: rejecting spoofing can mean protection is working. Its chart, domain counts and **View records** evidence all use the same seven UTC calendar dates, including today through the displayed snapshot time, bucketed by when reports arrived. Counts are messages, not report or record counts. The evidence dialog shows receiver, receipt time, source IP, disposition, aligned SPF/DKIM results and any supplied override/authentication evidence. The domain Sources page retains its separate 30-day view.

Authorised users also see **Integration and ingestion status**, explicitly global and unaffected by domain filters: the latest mailbox poll result, retained parse failures and enabled PSA configuration problems. Recent integration warnings/errors come from this instance's retained log buffer (up to five events in the last 24 hours), may already be resolved and reset on restart. A ready configuration or an empty log buffer is not a successful live connection test. Polling diagnostics remain collapsed below the queues. **Add domain** opens Inventory's existing creation control with the current group context and permissions.

Drill into any domain for a 30-day pass/quarantine/reject chart, its DMARC record status, and a breakdown of why any rejected/quarantined mail happened - a benign forwarder tripping alignment reads very differently from no reason given at all:

### Which services are sending

Above the per-IP table, the Sources tab has a **Senders** table with one row per sending service your reports point to, such as Microsoft 365, Google Workspace or Mailchimp:

* **Messages and Share** are how much of the domain's mail the service sent in the last 30 days.
* **Evidence** is a score of the signals dotMARC found for that service, with a label of strong, moderate or weak. It is not a probability, and it never reaches 100%. Open a row to see the signals behind it.
* **Pass rate and Failing** show how much of its mail passed DMARC, and how much was quarantined or rejected.
* **Fix** says what is failing and what to do about it, naming the service. It appears only when some of that service's mail is failing.

The signals are:

* an SPF or DKIM domain in the report that belongs to the service
* the DKIM selector the service is known to use
* who owns the sending IP
* the sending IP falling inside an IP range your domain's own SPF record authorises for the service, which is a strong signal
* the service being included in the domain's own SPF record without a matching IP, which is the weakest signal because it shows what is allowed to send, not what did

dotMARC reads those SPF ranges when it runs the daily SPF check, by following the record's `include:` and `redirect=` entries. The evidence says "Your SPF record authorises this IP for" the service. It does not say confirmed: a range shared by many customers of a service shows the service, not that this particular sender is yours. Only entries that authorise count, so a `-ip4:` or `~ip4:` entry is ignored. If the check can't read the record, the last ranges dotMARC read are kept.

Mail from a properly set up Microsoft 365 or Google Workspace signs as your own domain, so it is recognised by its IP owner and DKIM selector instead.

Sources that match no known service are listed last as **Not matched to a known service**. That means dotMARC could not match them, not that they are bad. The matching is worked out each time you open the page, so it improves as dotMARC learns more services, and it also names the service in failure recommendations, client reports, the client portal and the `service` field of the sources API.

### Decide which senders are authorised

The **Decision** column is where your team records what it has decided about a sender on this domain:

* **Authorised**: it should send as this domain.
* **Unauthorised**: it should not.
* **Under review**: you are still finding out, for example waiting for the client to answer.
* **Unreviewed**: nobody has decided yet. This is the default.

Select **Decide** (or **Change**, once there is a decision) beside the status, pick a new one, add an optional note, and save. Hover over a status to see where it came from: this domain, its group, or the baseline. A decision never changes DNS and never blocks mail, because your DMARC policy decides what receivers do. It does change what dotMARC tells you:

* A sender with no decision raises a **new sender** alert when it first appears, and counts towards "senders need a decision" on the Overview. Authorised and Under review both stop the alert and the count.
* An **Unauthorised** sender whose mail is still being delivered raises an alert (see [Alerts](./alerts.mdx)).
* The **Fix** column changes, as described below.
* Client reports summarise the decisions, and the [API](./api.mdx) returns each sender's decision.

The row shows who decided and when, and every change is recorded in the [audit log](./audit-log.mdx).

The **Fix** column changes with the decision:

* An **Unauthorised** sender is not asked to be fixed. If its failing mail is all blocked, the row says your policy is blocking it. If some was still delivered, it says how much and what your policy means for that: at `none` nothing is blocked, at `quarantine` it goes to spam, and at `reject` receivers should refuse it.
* An **Unauthorised** sender whose mail passes DMARC is flagged first, because it means the sender authenticates as your domain. Decide whether it should be authorised, or remove its access.
* An **Authorised** sender gets no fix while its mail passes. If some of it fails, the row says you authorised it but it is failing, and keeps the fix.

Open a service row to decide on a single IP address. An IP decision overrides the decision on its service, and the other IPs show "same as the service". A source in the Not matched row has no service, so you decide on its IPs.

Changing decisions needs the **SenderReview** permission, which the Admin role has. Custom roles can be given it on the Access page. Anyone who can see the domain can see the decisions.

The domain's Overview tab shows how many senders still have no decision, with a **Review** button that opens the Sources tab, and it goes away once every sender has one. The sources API returns each source's decision in a read-only `decision` field: `Authorised`, `UnderReview`, `Unauthorised` or `Unreviewed`. [Client reports](./client-reports.mdx) say how much mail from unauthorised senders was blocked or delivered.

dotMARC also raises two [sender alerts](./alerts.mdx#sender-alerts): one when a new sender appears that nobody has reviewed, and one when mail from a sender you marked Unauthorised is being delivered.

#### Set an answer once for many domains

You don't have to decide the same sender on every domain. Decisions can be made at three levels, and the most specific one wins:

1. **The domain's own decision**, on the service or on a single IP. It overrides everything below.
2. **The group's defaults**, set from **Manage > Groups** with the **Sender defaults** button on a group.
3. **The baseline**, set from **Manage > Baselines > Sender**. It applies to every domain.

For example, authorise Microsoft 365 in the baseline, mark it Unauthorised in the defaults of a client group that has moved away from it, and authorise it again on one domain of that client that still uses it. Each row in the Senders table says where its decision came from: set on this domain, from a group, or from the baseline. Choosing **Reset to inherited** in the dialog removes the domain's own decision, so the row falls back to the level below.

* A baseline or group decision only matters on a domain whose reports show that service. Nothing is added to domains that don't use it.
* The **Domains** column on the baseline and group defaults pages says how many monitored domains show each service in their last 30 days of reports, so you can see how far a decision reaches. **Found** means strong evidence and **likely** means the service is attributed on weaker evidence. It uses the same evidence as the Senders table, and the owner of an address only counts once that address has been looked up, so a likely count can rise as lookups finish. On a group's page it counts only that group's domains.
* If a domain is in several groups that disagree, the most cautious decision wins: Unauthorised, then Under review, then Authorised. The row says which groups disagree, and a decision on the domain itself settles it.
* A sender left Under review can be reminded about. The new sender [alert rule](./alert-rules.mdx) can count Under review as undecided, or alert again after a number of days. By default Under review stops the alert.
* The baseline can be changed only by someone who isn't limited to particular groups. A person limited to some groups can change the defaults of their own groups, and no others.
* If a service later leaves dotMARC's list of known services, its decision is kept and shown as "no longer recognised", with a button to remove it.

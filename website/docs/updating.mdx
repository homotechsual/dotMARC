# Update or redeploy dotMARC

The newest release is <LatestVersion />. See [Releases and Updates](/releases-updates) for what changed in it and in earlier versions.

## Before you update

* **Read the release notes** for every version you are skipping. Each one has an **Upgrading** section that says whether anything needs your attention, such as a new permission or setting.
* **Your data is kept.** Reports, settings and secrets live in PostgreSQL, so an update replaces only the application. Never remove the database volume, and never add `--volumes` to `docker compose down`.
* **Migrations run by themselves** when the new version starts. An older version isn't always compatible with a newer database, so take a PostgreSQL backup first if you might need to roll back.
* **Prefer a release tag to `:latest`** in production. A tag such as <code>:<LatestVersion /></code> says exactly what is running and what to go back to. `:latest` moves under you and needs an extra step to pick up a new build.

## Try upcoming changes with `:next`

Every change merged to the `develop` branch is built and published as `ghcr.io/homotechsual/dotmarc:next` (also `homotechsual/dotmarc:next` on Docker Hub), for Linux on amd64 and arm64. It is the code being prepared for the next release, so it changes often and can break. Use it to try a feature early or to check a fix, never for production.

* **It marks itself.** A `:next` container shows a "Dev build" banner at the top of every page, and the footer reads
  <code>v&lt;version&gt; (dev)</code> with the version being worked towards. That version has no release notes yet, so it doesn't
  link to any.
* **Use a separate database.** `:next` can run migrations a released version doesn't understand, so don't point it at data you want to keep. Moving back to a release afterwards means restoring a backup taken before.
* **You can try it without installing.** [next.dotmarc.app](https://next.dotmarc.app) runs `:next` with the same simulated data as the demo.
* **Pull to update.** `:next` is replaced on every build, so `docker compose pull` fetches the latest. Use `:next-<commit>` instead when you need to stay on one build.

## Check it worked

* Open dotMARC and look at the version in the footer. It links to that release's notes.
* Check **Manage > Logs > Server** for new warnings or errors. See [Server logs](./server-logs.mdx).
* On Azure, follow [Verify the update](./deploy-to-azure.mdx#verify-the-update) to confirm the new revision is healthy and taking traffic.

## Roll back

Go back to the previous release tag and recreate the application, the same way you updated. The detailed steps, including the database caveat, are in [Docker: Roll back](./deploy-with-docker.mdx#roll-back) and [Azure: Roll back](./deploy-to-azure.mdx#roll-back). Don't roll back blindly after a release that applied database migrations, because the older version has to work with the schema the newer one left behind.

# Permissions & Access

dotMARC uses a fine-grained permissions model so internal staff and external clients can be granted access the same way, by email, with an optional scope rather than an all-or-nothing login.

## Roles

A **Role** is a named bundle of permissions. Two are built in:

* **Admin**: every permission, locked (its name and permission set can never be changed or deleted).
* **Viewer**: read-only (`DomainsView`, `GroupsView`, `TagsView`, `AlertsView`), and the only role that can be restricted to specific Groups.

Admins can also create custom roles covering any subset of the available permissions, domain management, Group/Tag management, access management, MTA-STS hosting (`MtaStsView`, `MtaStsManage`), [alerting](./alerts.mdx) (`AlertsView`, `AlertsManage`, which also covers adding and editing the [destinations](./alerts.mdx#destinations) alerts are sent to), DNS provider push configuration (`DnsPushManage`), viewing the in-app [server logs](./server-logs.mdx) (`LogsView`), reading or setting retention for the [audit log](./audit-log.mdx) (`AuditView`, `AuditManage`), marking senders as authorised or unauthorised (`SenderReview`), and creating, changing, ordering and deleting [alert rules](./alerts.mdx) (`AlertRulesManage`) are each independently grantable. The Admin role has `AlertRulesManage`; a custom role has to be given it on the Access page. Setting [DMARC targets](./baselines.mdx#domain) is its own permission, `BaselinesManage`, described under [Baselines](#baselines).

## Baselines

`BaselinesManage` lets someone set the target DMARC policy on the [Baselines](./baselines.mdx#domain) Domain tab, with **Domain baseline** on the Groups page, and on a domain's target card. What a holder can change follows their group scope, as with sender decisions:

| Who holds `BaselinesManage` | System target | Group target | Domain target |
| --- | --- | --- | --- |
| Staff with no group limit | Yes | Any group | Any domain |
| Staff limited to some groups | No (shown read-only) | Their own groups | Domains in their groups |
| Client portal users | No | No | No |

Viewing a domain's effective target needs only `DomainsView`. Pushing a raised policy to DNS still needs `DomainsEdit`, so setting a standard and applying it can be held by different people. The Sender tab keeps `SenderReview`.

The Admin role gets `BaselinesManage` automatically when you upgrade. Custom roles do not, so nobody gains the power by upgrading: add it to a custom role on the Access page.

## Granting access

Access is granted from the **Manage Access** page: type an email, pick a role, and if the role is Viewer, optionally pick which Groups they can see. This works identically whether the person is internal staff or an external client contact.

* A grant made before someone's first sign-in stays pending until they actually authenticate, at which point it binds to their stable Entra object ID.
* A Viewer scoped to specific Groups can only ever see domains in those Groups enforced at the data-query level, not just hidden in the UI, so this holds even via direct URL navigation to a domain outside their scope.
* An unscoped Viewer grant (no Groups selected) sees every domain, the same as before scoping was introduced.
* A Group-scoped grant can also be switched to the [client portal](./client-portal.mdx): a simplified, branded, read-only view of the client's own domains instead of the dotMARC dashboard.

## Bootstrapping the first Admin

See [Getting Started](./getting-started.mdx#configure) and [Deploy to Azure](./deploy-to-azure.mdx) the `InitialAdmins__Emails` environment variable grants Admin to the listed emails the very first time the app starts with no existing access grants. This is the only way to establish the first Admin; set it before your first deploy.

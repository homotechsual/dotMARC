# dotMARC 0.14.0 roadmap

**Headline:** bulk DNS push, per provider. Everything else in 0.14.0 is smaller work that does not touch the push engine and can land alongside it. Ticketing in alert rules moves to 0.15.

This is a roadmap, not a task plan. Each item points at its spec. Detailed implementation plans are written one slice at a time, when that slice is about to start, in the same form as the 0.13 plans.

## Decisions so far

* **Headline (user):** bulk DNS push. Ticketing in alert rules becomes the headline of 0.15, with its direction kept in the notes (per-rule PSAs are All or Selected).
* **Group-limited rule (user):** a group-limited editor can only use their own groups and cannot remove the last group that gives them access. It is enforced for API keys in 0.14.
* **Planning calls on bulk DNS push (mine, marked so they can be corrected):**
  * The batch size limit starts at 50.
  * `dmarc-auth` is not in the first version. `dmarc`, `tlsrpt` and `mta-sts` are.
  * A retry of failed domains needs a fresh sign-in. The provider session is never kept past the batch.
  * A domain that would lose a CNAME delegation is unticked by default in the review and needs an explicit tick.
  * A fake demo DNS push provider is part of the work. Today the demo registers only the three real providers, so it cannot show a push at all, and the browser checks need it too.

## Order

1. Item 0, then items 8 and 4, which are tiny and independent. They also exercise the new deploy filters on real code changes.
2. Slice A (item 1). It is the risky part and has no UI, so it can be proven with tests against a fake provider before anything depends on it.
3. Items 5 and 6 can be done while slice A is being reviewed or tested, since they share no code with it.
4. Slice B (item 2), then slice C (item 3). Item 7 starts with its spike once slice B's page work is out of the way, since both touch the Dashboard.

5. Items 9 to 12 come from the baselines and dashboard spec and are small and independent of the push engine. Item 9 can go in at any point. Items 10 and 11 go with item 5, since they are on the same page. Item 12 goes in before slice B.

If bulk DNS push slips, items 4 to 12 are independent and could ship on their own as 0.14.0, with bulk push as 0.14.1 or 0.15.

## Not in 0.14.0

* **Ticketing in alert rules** (0.15). Slice 1 retires the global and group ticket panels into rules with a migration, slice 2 adds delayed and on-escalation tickets, slice 3 adds per-PSA ticket parameters.
* **Dropping the retired settings columns** (about 25 on `NotificationSettings`, kept "for one release" in 0.13). Proposed for 0.15 with the ticketing migration, since both are cleanups of the settings and rules model and an install upgrading straight from 0.12 would lose its thresholds if the columns went first (the rules are seeded from them lazily, by app code). Needs the user's call, see below.
* DKIM automatic mode and the missing-key alert, bulk `dmarc-auth`, pre-release (beta) publishing.
* **The rest of the [baselines and dashboard spec](../specs/2026-11-20-domain-baselines-security-score-and-dashboard-design.md):** baseline profiles, drift view, secure score, managed DMARC and DKIM pushes, provider DKIM enumeration, domain-age rule conditions, Forwarder decisions, the unified Filters button, the polling status change, the Add domain box and the dashboard sender-review indicator. Each has open decisions listed in the spec. The Filters button also collides with slice B's selection UI and the list-position work.
* **Slice B note:** the spec's managed DMARC and DKIM changes are meant to reuse the bulk push review, so slice B keeps the review and result screens generic over the target. `DnsPushBatchService.BulkTargets` is already a list.

## Release gates

The ones 0.13 used, plus:

* A real push to each of the three providers against a test zone, in slice C. The fake provider proves the logic and not the provider's token and rate limit behaviour.
* The demo and next show a bulk push end to end.
* The upgrade note says what changes for someone running the three providers.

## Settled with the user

1. **Test zones:** the user has unused domains across several Cloudflare accounts, so slice C verifies against real Cloudflare zones, including whether one sign-in covers zones in more than one account. Azure DNS and Google Cloud DNS have no test accounts yet: they are checked against the providers' documentation until accounts exist, and the release notes say which providers were verified live.
2. **The legacy columns:** dropped in 0.15 with the ticketing migration, as proposed.
3. **Items 5 to 8** all stay in 0.14.0.

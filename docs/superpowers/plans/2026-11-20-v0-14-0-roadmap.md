# dotMARC 0.14.0 roadmap

**Locked scope (22 November):** bulk DNS push, per provider; an action-centre Dashboard; a separate Domain Inventory; and the agreed correctness/UX fixes. Baselines and the secure score are not part of 0.14; the user subsequently assigned the deferred tranche to 0.15 alongside ticketing.

**Scope revision (24 November, user):** three items join 0.14. The DMARC target policy (system, group and domain targets, the first slice of baselines) is the first feature of 0.14, ahead of slice B, and brings a tabbed Baselines page. Alerts & PSA and Logs become tabbed pages in the same pattern. Baseline profiles, drift views and the secure score stay in 0.15.

Public release planning is tracked in the [0.14 milestone](https://github.com/homotechsual/dotMARC/milestone/9) (issues #43-#54, #75-#77) and [0.15 milestone](https://github.com/homotechsual/dotMARC/milestone/10) (issues #55-#65). These are feature-level issues rather than one issue for every implementation task. Both milestones have no committed due date.

This is a roadmap, not a task plan. Each item points at its spec. Detailed implementation plans are written one slice at a time, when that slice is about to start, in the same form as the 0.13 plans.

## Decisions so far

* **Headline (user):** bulk DNS push. Ticketing in alert rules becomes the headline of 0.15, with its direction kept in the notes (per-rule PSAs are All or Selected).
* **Group-limited rule (user):** a group-limited editor can only use their own groups and cannot remove the last group that gives them access. It is enforced for API keys in 0.14.
* **Action centre (user, 22 November):** use existing health, report and sender-decision facts. Move the full domain list and bulk selection to Domain Inventory. Include unified filters, sender-review visibility, compact polling status and domain entry. Do not introduce a baseline engine or an approximation labelled as the secure score.
* **Planning calls on bulk DNS push (mine, marked so they can be corrected):**
  * The batch size limit starts at 50.
  * `dmarc-auth` is not in the first version. `dmarc`, `tlsrpt` and `mta-sts` are.
  * A retry of failed domains needs a fresh sign-in. The provider session is never kept past the batch.
  * A domain that would lose a CNAME delegation is unticked by default in the review and needs an explicit tick.
  * A fake demo DNS push provider is part of the work. Today the demo registers only the three real providers, so it cannot show a push at all, and the browser checks need it too.

## Locked action-centre contract (22 November)

The user's mock-up proposes making Dashboard an action centre: actionable summary counts, a seven-day quarantine/reject chart, a domain-health distribution, Domains with Problems and Domains with Quarantines/Rejects queues, with the full domain inventory on a separate page. The detailed workflow and acceptance criteria are in [the dashboard spec, section 7](../specs/2026-11-20-domain-baselines-security-score-and-dashboard-design.md).

This scope revision is accepted and represented by items 13 to 19 above. Use existing check/report/sender facts for the queues. Defer both the baseline-aware secure score and health-distribution chart; do not substitute an unlabelled approximation.

**Confirmed direction:** move the full domain inventory to its own page, leaving Dashboard as the action centre. The inventory route and reuse of existing management surfaces remain implementation decisions.

* **Problem queue:** confirmed DNS failures, overdue expected reports and outstanding sender decisions. Unknown required checks are separately labelled "needs checking", not confirmed failures. Apply existing null-domain exceptions consistently.
* **Priority:** operational failures first; domain problems ordered by severity, with deterministic tie-breaking specified in the detailed plan. Each entry names the problem and links directly to the relevant action.
* **Investigation queue:** non-zero quarantine/reject message volume in the last seven days, even for domains with healthy DNS. Counts and chart/drill-down windows must match. Enforcement against spoofing is not automatically a configuration failure.
* **Windows:** seven days for quarantine/reject volume; explicitly labelled 30-day pass rates; sender-review counts use Domain Overview's existing window.
* **Polling:** retain details on Dashboard, collapsed by default. Failure status stays visible. Show existing operational alerts without per-rule ticker configuration.
* **Inventory and filters:** preserve read-only access, saved preferences and return navigation; bulk selection belongs to Inventory. One Filters entry point replaces separate Groups/Tags buttons.

Detailed plans still choose routes, responsive layout, component reuse and preference migration mechanics. These are implementation decisions inside the locked boundary, not permission to expand it.

## Release gates

The ones 0.13 used, plus:

* A real push to each of the three providers against a test zone, in slice C. The fake provider proves the logic and not the provider's token and rate limit behaviour.
* The demo and next show a bulk push end to end.
* The upgrade note says what changes for someone running the three providers.
* Dashboard counts and drill-downs agree under identical filters and permissions; read-only users retain inventory access.
* Inventory preserves grouped views, saved defaults, list-position restoration and authorised bulk review.
* Seven-day quarantine/reject totals count messages and match the investigation list; DNS health and rejected spoofing are not conflated.
* Null-domain regressions are covered, including genuine DMARC weakening, absent/revoked/usable known DKIM keys and failed DNS lookups.
* Browser checks cover direct review actions, collapsed polling failure visibility, unified filters, domain entry and responsive layout.

## Release notes (draft)

### DMARC targets

* Set the DMARC policy your domains should reach at three levels: system-wide, per group and per domain. `sp` follows `p` unless you set it, and a target is only met at `pct=100`.
* A domain uses its own target, else the strictest target among its groups, else the system target. A group's target replaces the system target even when it is weaker.
* A new alert, "DMARC policy below target", is enabled by default. It does not open PSA tickets by default and never fires for a domain with no target.
* The DNS push now writes the effective target into new DMARC records and raises existing records that fall short, including removing a `pct` below 100. It never lowers a stricter policy.
* Baselines replaces Sender baseline, with a Sender tab and a Domain tab. The old `/senders/baseline` link redirects.
* The Dashboard has a Target filter, and the API returns `dmarcTarget` on domains with a `dmarcTarget` list filter.
* New permission `BaselinesManage` covers setting targets. Admin has it after upgrading. Custom roles do not until someone adds it on the Access page.
* Nothing changes until a target is set: no new alerts, no counts and no change to pushes.
* A domain whose latest DMARC lookup failed is judged on the last policy dotMARC read. Only a domain never checked shows "Needs checking".
